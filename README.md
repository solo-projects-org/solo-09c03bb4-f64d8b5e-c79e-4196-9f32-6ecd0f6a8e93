# Delta Lake 版本可恢复性分析网页

对象存储故障后，湖仓值班员用本工具查清一张 Delta Lake 表还有哪些
版本可以完整回退。值班员在网页上填写版本区间，上传三类材料：

1. `_delta_log` 中留存的 **JSON 提交**（`NNN.json`，20 位补零版本号）；
2. 留存的**经典单文件 Parquet 检查点**（`NNN.checkpoint.parquet`，用 PyArrow 读取）；
3. **现存数据文件的表内相对路径清单**（每行一个路径，如 `data/part-00000-….parquet`）。

故障现场通常能抢救出**两批备份**的日志。页面提供**批次 A / 批次 B**
两个日志选择框，两批一并提交、合并核查：

- 同名（同版本）的 JSON 提交或经典单文件检查点，**所有副本字节一致
  才去重**，只解析一份；
- 任意副本**内容有出入**即判定冲突：报告列出文件名，**整组副本都不用**，
  结论与上传顺序无关；
- 每版从**不晚于目标版的最新无冲突检查点**起算重放，没有可用检查点
  就从 0 版提交查起；
- 重放所需的**冲突提交**与**未上传的提交**在逐版报告中分开列出；
- **因冲突不能重建的版本不显示文件核对结果**，其余版本照常核对。

逐版重放 `add` / `remove` 动作后，把重建出的快照引用文件与现存清单核对：

- 🟢 **可重建 · 文件齐全**：重放连续无断档，且快照引用的数据文件全部现存；
- 🟣 **同名日志冲突，无法重建**：重放所需的提交因同名副本内容不一致被整组弃用；
- 🔴 **缺失提交，重放中断**：明确给出未上传的提交号（版本号列表）；
- 🟠 **重放完整但缺数据文件**：明确给出每个缺失的数据文件表内相对路径。

**仅处理无删除向量（Deletion Vector）的表**：协议特性或任何 add/remove
动作中出现 `deletionVector` 时直接拒绝分析，并指出来源文件。

## 目录结构

```
app/
  analyzer.py            # 核心逻辑：日志解析、同名副本比对、逐版重放、文件核对、DV 拦截
  web.py                 # Flask 路由：两批上传分析 + 本地样例 API
  templates/index.html   # 单页界面（服务端渲染与 JS 渲染共用）
scripts/generate_samples.py  # 用 PyArrow 构造两套样例 Delta 表
samples/
  healthy_table/             # 健康表（单批留存）
    _delta_log/
    existing_files.txt
  incident_table/            # 误删事故表（两批备份）
    batch_a/_delta_log/      # 批次 A：主存储事故前的备份（v0–v4）
    batch_b/_delta_log/      # 批次 B：副本存储的备份（v2–v5）
    existing_files.txt
tests/                   # pytest：核心逻辑与路由测试
Dockerfile / docker-compose.yml
```

## 用 Docker Compose 启动

```bash
docker compose up --build
# 打开 http://localhost:8000
```

页面下半部有两个按钮可**直接加载本地样例**，无需手动选择文件：

- **健康表样例（v0–v4）**：单批留存，含 v2 检查点，5 个版本全部可重建；
- **误删事故样例（v0–v6）**：两批备份 `batch_a` / `batch_b` 一并加载。
  两批中 v2 / v4 提交与 v4 检查点字节一致（自动去重）；**v3 提交与
  v2 检查点内容不一致**（判冲突、整组弃用）；v6 提交两批都没有；
  数据文件 `part-00004` 已随事故删除。预期结论：

  | 版本 | 结论 | 说明 |
  |---|---|---|
  | v0–v2 | 🟢 可重建 | v2 检查点冲突弃用，改从 `commit-0` 重放 |
  | v3 | 🟣 冲突 | v3 提交两批内容不一致被弃用，且无 ≤v3 的可用检查点；不显示文件核对 |
  | v4 | 🟠 缺数据文件 | 以无冲突 `checkpoint-4` 为基线，缺 `data/part-00004-incident.parquet` |
  | v5 | 🟠 缺数据文件 | 同上，缺 `part-00004` |
  | v6 | 🔴 缺提交 | v6 提交两批都未上传（与冲突分开列出），仍照常核对文件 |

  批次 B 中还放了一个分片检查点残片，工具会明确列为“已忽略：仅支持
  经典单文件检查点”。

## 手工上传分析（含两批备份）

1. 填写“起始版本 / 结束版本”；
2. **批次 A** 选择第一批留存的 `.json` 与 `.checkpoint.parquet`，
   **批次 B** 选择另一批备份的同名目录文件，两批一并提交
   （文件名必须保持 20 位补零版本号，上传时带不带目录前缀都可以）。
   用内置样例练手：批次 A 选 `samples/incident_table/batch_a/_delta_log`
   下全部文件，批次 B 选 `batch_b/_delta_log` 下全部文件；
3. 上传现存数据文件清单（支持 `#` 注释、空行、`./` 前缀、URI 编码路径，
   两侧路径会做同一归一化）；不上传清单则所有引用文件都判为缺失；
4. 提交后得到总览统计、输入材料盘点（已识别提交 / 检查点、冲突弃用
   文件、去重文件、忽略文件）和逐版核对明细（可展开查看每个引用文件
   的 ✓ / ✗ 状态；冲突版本明确提示不核对文件）。

也可以只上传检查点：对不晚于检查点版本的目标版本，直接以检查点中的
add 列为快照基线；目标版本更新时，则从检查点版本 +1 起连续重放提交，
中途缺任一提交即报缺失提交号。检查点里的 remove 是墓碑，不属于快照。

## 设计取舍

- **同名副本字节比对**：两批备份的同名提交 / 检查点先按字节分组比对，
  全部一致才去重；任何出入都整组弃用并列出文件名。宁可少用一个版本，
  也不让上传顺序左右核查结论；
- **基线选择**：优先使用不晚于目标版本的最新**无冲突**检查点（重放
  距离最短），无检查点时才要求版本 0 的提交；冲突的检查点在归类阶段
  已整组剔除，不参与基线选择；
- **逐版独立重放**：每个目标版本都从基线完整重放一次，缺提交或冲突
  不会污染其他版本的结论，报告中的“重放起点”对每版透明；
- **冲突与缺失分列**：重放所需的提交按“同名冲突弃用”与“两批均未上传”
  分开列出；冲突版本不展示文件核对结果，避免半截快照误导核对；
- **只认经典单文件检查点**：分片检查点（`N.checkpoint.K.M.parquet`）
  与 `_last_checkpoint` 指针不参与重放，只在页面登记忽略原因；
- **DV 硬拦截**：删除向量会让“文件存在 ≠ 行数据完整”，超出本工具
  基于文件清单的核对能力，因此在协议层和动作层双重检测并拒绝。
